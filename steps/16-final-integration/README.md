## חלק 1 — קודם מבינים (בשפה פשוטה)

### 1.1 למה מגדילים רק בסוף?
משרד החינוך דורש **6 מחלקות × לפחות 8 מחשבים** בכל סניף (דרישה 20.2). הבנייה עם 2 מחשבים לכל מחלקה
הפכה את המעבדה למהירה וקלה לקריאה. מכיוון שעכשיו הכול אוטומטי (DHCP, ‏SLAAC, ‏port-security ‏sticky),
הוספת מחשבים היא רק לגרור, לחבר כבל ולשנות שם.

### 1.2 איך דואר אלקטרוני עובד ב-Packet Tracer
- **שרת הדואר** מחזיק תיבות דואר (`eng1@intel.lab`) — כמו סניף דואר עם תאי דואר.
- **לקוח הדואר** במחשב שולח דואר לשרת (SMTP) ואוסף את הדואר שלו (POP3).
- הלקוח מוצא את השרת לפי **שם** (`mail.intel.lab`) ‏←‏ בגלל זה ה-DNS היה צריך לעבוד קודם.

חיפה וירושלים משתמשות בשרת הדואר שב-DMZ (ירושלים דרך ה-VPN). קריית גת משתמשת בשרת דואר IPv6 משלה
(`kg.intel.lab`).

### 1.3 בדיקה = הוכחה
הבוחן נותן ציון על מה שאתם יכולים **להראות**. כל דרישה צריכה בדיקה שאפשר להריץ בזמן אמת וצילום מסך
בספר הפרויקט.

## משימה 2 — מוסיפים מחשבים למחלקה אחת, בזהירות
🧠 **למה:** עושים מחלקה אחת לאט, עם כל הבדיקות. אחרי זה, כל השאר הוא חזרה.

👉 **דוגמה:** **הנדסה** בחיפה — צריך את PC-HFA-ENG-04 … 08 ‏(5 מחשבים חדשים).

👣 **צעדים:**
1. מחזיקים **Ctrl**, לוחצים על סמל ה-**PC** ‏(End Devices), ואז לוחצים **5 פעמים** ליד SW-HFA-A-ACC1
   ‏←‏ לוחצים **Esc** ‏(M3).
2. משנים את השמות ל-`PC-HFA-ENG-04` … `PC-HFA-ENG-08` ‏(M4).
3. מחברים כל אחד (**Straight-Through**, ‏**FastEthernet0** של המחשב) לפורט ההנדסה הפנוי הבא (M5).
   מחלקים אותם בין שני המתגים:

   | מחשב | מתג | פורט |
   |---|---|---|
   | PC-HFA-ENG-04 | SW-HFA-A-ACC1 | Fa0/3 |
   | PC-HFA-ENG-05 | SW-HFA-A-ACC2 | Fa0/3 |
   | PC-HFA-ENG-06 | SW-HFA-A-ACC1 | Fa0/4 |
   | PC-HFA-ENG-07 | SW-HFA-A-ACC2 | Fa0/4 |
   | PC-HFA-ENG-08 | SW-HFA-A-ACC1 | Fa0/5 |

4. כל מחשב ‏←‏ **Desktop → IP Configuration → DHCP** ‏(M16).
5. כל מחשב ‏←‏ **Command Prompt** ‏←‏ `ping 10.10.16.1` (השער) — כדי ש-port-security ילמד את ה-MAC שלו.

✅ **אמורים לראות:** לכל מחשב יש כתובת ‎`10.10.16.x` וה-ping מקבל תשובות.

❌ **למחשב יש ‎`169.254.x.x`:** הוא בפורט מחוץ לטווח, או שהפורט כבוי (חניה). בודקים עם
‏`show vlan brief` במתג.

## משימה 7 — סבב ההקשחה האחרון

```
show running-config | include hostname|banner|enable secret|service password|ip ssh|logging|ntp server
```
✅ **כל אחד חייב להציג:** ‏hostname לוגי, ‏banner, ‏`enable secret`, ‏`service password-encryption`,
‏`ip ssh version 2`, ‏`logging host`, ‏`ntp server`.

```
show running-config | section vty
```
✅ ‏`transport input ssh` + ‏`access-class` (או `ipv6 access-class` בקריית גת).

## משימה 10 — מגינים: השאלות הסופיות בקול
הבוחן שואל "למה?" על כל בחירה. עונים **בקול, בלי דפים**, ואז פותחים את התשובות ומשווים:
1. למה ה-area של בניין C לא מחובר ל-area 0, ומה ה-virtual link עושה?
2. למה ה-ASA לא עושה NAT בתכנון הזה?
3. למה GRE over IPsec ולא IPsec רגיל?
4. למה ה-HSRP active הוא תמיד גם ה-STP root של אותו VLAN?
5. מה קורה לירושלים אם R-JLM-EDGE מת? איך הייתם מתקנים?

<details dir="rtl"><summary>✔ תשובות קצרות</summary>

1. כדי לעמוד בדרישות 8/22.16 ולהראות את הכלל "כל area חייב לגעת ב-area 0". ה-virtual link הוא חיבור
   לוגי של area 0 דרך area המעבר 2, בין B-DIST ‏(ABR 0/2) ל-C-DIST ‏(ABR 2/3).
2. כדי שכתובות פרטיות יעברו את ה-ASA בלי שינוי — נקודת NAT אחת (נתב הקצה) פשוטה יותר, וה-VPN רואה את
   כתובות ה-10.x האמיתיות.
3. ה-static NAT של שרת ה-web היה מתרגם את התשובות שלו ב-VPN לפני ההצפנה; תעבורה דרך ממשק מנהרת GRE
   (שהוא לא ממשק NAT) לא מתורגמת. ‏GRE גם מאפשר בעתיד להעביר פרוטוקולי ניתוב דרך המנהרה.
4. כדי שהדרך לשער תהיה קצרה — אחרת מסגרות עוברות בקישור שבין מתגי ה-distribution בלי סיבה.
5. ירושלים מאבדת את האינטרנט ואת ה-VPN (נקודת כשל יחידה). פתרון: נתב קצה שני + קישור שני לספק, ‏HSRP
   ביניהם, ומנהרה שנייה לחיפה.
</details>
